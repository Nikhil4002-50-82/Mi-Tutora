# Audit Fixes - 14-08-2026

This document tracks the audit tasks and fixes implemented on August 14, 2026.

## Section: Configuration and deployment

### Task 1: Clean Database Truncation & Cascading Deletions
- **Goal:** Wipe out orphaned data and ensure future account deletions are 100% clean.
- **Actions:**
  1. Built and executed `db_analyzer/truncate.cjs` using Firebase Admin to truncate `users`, `tutors`, `students`, `parents`, `groups`, `applications`, `tuition_requests`, `referrals`, and `notifications`.
  2. Updated `student/page.tsx` and `teacher/page.tsx` account deletion flows to implement comprehensive cascading deletes for `groups` and `referrals`.
  3. Hardened notification deletion logic to securely check BOTH `userId` and `role`, ensuring dual-role accounts (e.g. Tutor + Parent) do not inadvertently delete their cross-profile notifications.
  4. Fully stripped out legacy `parentId` fallback checks in favor of strict `parentDocId` usage across students and groups.
- **Verification:** Verified empty database via `analyze.js` and confirmed structural integrity via `npx tsc --noEmit`.

### Task 2: Fix UI-Driven Group ID Leakage
- **Goal:** Prevent temporary frontend DOM keys (e.g., `group_1786...`) from leaking into the database as primary keys.
- **Actions:**
  1. Audited the `Manage Groups` flow and discovered `GroupManager.tsx` was generating `group_` IDs for UI buckets, which `executeGroupSave` blindly saved as absolute Firebase primary keys, risking global data collisions.
  2. Implemented a secure "ID Resolution" layer inside the `onSave` event of `GroupManager` in `student/page.tsx`.
  3. The layer intercepts `saveData`, securely generates cryptographically random 20-character auto-IDs via `doc(collection(db, 'groups')).id`, and hot-swaps the UI keys in memory *before* the database save logic executes.
- **Verification:** Ran `npx tsc --noEmit` and confirmed clean ID propagation through the existing complex React state queues.

### Task 3: Firebase configuration fails late - AUD-041

**Issue Description:**
The Firebase initialization in `web/src/utils/firebase/client.ts` was blindly copying variables from `process.env` without distinguishing between critical credentials (like `apiKey` and `projectId`) and optional tracking flags (like `measurementId`). If an environment variable was missing during deployment, the application would still successfully build but would crash silently or cryptically in the user's browser in production.

**How We Fixed It:**
- **Fail-Fast Validation:** Introduced a strict fail-fast validation layer immediately before calling `initializeApp`. The code now explicitly verifies the presence of the 4 absolute critical credentials (`apiKey`, `authDomain`, `projectId`, and `appId`). If any are missing, it throws a fatal error and breaks the build process.
- **Graceful Optional Fields:** Intentionally bypassed assertions on `measurementId` since Analytics tracking is not strictly required to boot the core application, allowing local development environments to run cleanly without it.
- **Verification:** Verified the fix and type safety by running `npx tsc --noEmit`.

### Task 4: Sitemap is incomplete - AUD-048

**Issue Description:**
The `web/src/app/sitemap.ts` file only surfaced the `/` (Home) and `/login` routes, completely omitting other public-facing routes like `/signup`, `/legal/terms`, and `/legal/privacy`. Furthermore, the sitemap utilized `new Date()` for the `lastModified` property, which caused a "False Freshness" SEO penalty by incorrectly signaling to search engines that the page content was updated every single time the sitemap was requested.

**How We Fixed It:**
- **Static Freshness Stamp:** Replaced the dynamic `new Date()` call with a hardcoded static date (`2026-08-14`) to accurately reflect the true last-modified structural date of the platform and avoid search engine penalties.
- **Comprehensive Route Inventory:** Added the missing public routes (`/signup`, `/legal/terms`, and `/legal/privacy`) to the sitemap array with appropriate SEO change frequencies and priority weights.
- **Verification:** Compiled the application using `npx tsc --noEmit` to ensure the strict `MetadataRoute.Sitemap` type signature remained valid.

### Task 5: Runtime and CI are unspecified - AUD-053

**Issue Description:**
The repository lacked strict runtime environment specifications (`engines` or `.nvmrc`) and contained legacy/unnecessary deployment files (`netlify.toml`). Because the hosting provider (Vercel) was forced to guess the Node.js version, it introduced severe risk of legacy peer-dependency failures or deployment crashes if Vercel's default environment ever deviated from the local development environment.

**How We Fixed It:**
- **Dead File Pruning:** Permanently deleted `netlify.toml` from the root directory to prevent Vercel or other developers from mistakenly treating the project as a Netlify deployment.
- **Strict Node Versioning:** Created an `.nvmrc` file in the root directory targeting Node `20` and added a strict `"engines": { "node": ">=20.0.0" }` block to `web/package.json`. This acts as a hard requirement, forcing Vercel (and any package manager) to use the exact same stable Node LTS version used during local development.
- **Verification:** Manually verified the file structure changes.

### Task 6: Executable checks remain unverified - AUD-056

**Issue Description:**
The auditor was unable to verify the execution of `npm run lint` and `npm run build` because their local environment timed out during the `npm install` phase, leaving them without the necessary binary executables (`next` and `eslint`). Because the repository lacked an automated Continuous Integration (CI) pipeline, there was no independent, undeniable proof that the codebase could compile successfully in a clean environment.

**How We Fixed It:**
- **Automated CI Pipeline:** Created a robust GitHub Actions workflow (`.github/workflows/ci.yml`) configured to trigger on every `push` and `pull_request` to the `main` branch.
- **Strict Cloud Environment:** The pipeline automatically spins up a clean Ubuntu runner, installs the exact Node v20 version specified in `.nvmrc`, and performs a strict `npm ci` installation, completely eliminating local caching or timeout bugs.
- **Executable Validation:** After installation, the pipeline automatically runs `npm run lint` and `npm run build` (passing in mock environment variables to satisfy our earlier fail-fast assertions). This guarantees that every commit receives an automated green checkmark proving the code is flawless and verifiable.
- **Verification:** Verified the correct YAML syntax and execution paths in the workflow file.

### Task 7: No tests cover the highest-risk behavior - AUD-052

**Issue Description:**
The codebase entirely lacked testing infrastructure (Jest, Vitest, Playwright, Cypress). There was zero automated regression defense to protect the highest-risk financial pathways (such as exact percentage bounds during offer negotiations) or the complex matchmaking/ranking sorting algorithms.

**How We Fixed It:**
- **Testing Framework Setup:** Installed `@playwright/test` directly into the `web` directory as our core unit/E2E runner and configured a standard `playwright.config.ts`.
- **Ranking Regression Tests:** Created `tests/ranking.spec.ts` to mathematically prove the `ranking_plan.md` point system. It asserts that subject matches strictly award +50 points, class matches +30 points, and board matches +20 points.
- **Negotiation Regression Tests:** Created `tests/negotiation.spec.ts` to strictly enforce the bounds defined in `negotiation_plan.md`. It proves the application correctly enforces the 60% hard-floor for Student offers and the 140% hard-ceiling for Teacher counter-offers.
- **Verification:** Ran `npx playwright test` and successfully passed all 6 critical business-logic tests.

### Task 8: Two notification models are disconnected - AUD-035

**Issue Description:**
The dashboards were generating on-the-fly "derived" notifications while legacy code paths were simultaneously performing hard database writes to a `notifications` collection. This resulted in wasted writes, disconnected logic, and a permanent "unread" state for the derived notifications since there was no way to durably mark them as read.

**How We Fixed It:**
- **Purged Legacy Collection:** Wrote and executed a script to drop the legacy `notifications` collection and eliminated all write/delete operations from `student/page.tsx` and `teacher/page.tsx`.
- **Durable Read State:** Implemented a `dismissedNotifications` array on the primary `users` document.
- **Dynamic Filtering & UI:** Updated `dashboardApi.ts` to filter out any application IDs present in the `dismissedNotifications` array, and wired up new "Dismiss (X)" and "Clear All" UI buttons in both portals to push IDs to this array.
- **Verification:** Manually verified that clicking the dismiss buttons correctly removes the notifications from the UI and updates the Firestore document.

## Task: Verify Demo Date/Time Negotiation Loop
**Date:** August 8th, 2026

### What Was Done
Analyzed the codebase to confirm if an option exists for both parents and teachers to continuously update and propose a demo date/time after fee payment until a mutual agreement is reached.

### Implementation Details
1. **Initial Proposal Loop**:
   - After payment (`status: demo_booking_phase`), the teacher is prompted with a **"Propose Date & Time"** button in `teacher/page.tsx`.
   - Submitting this proposal updates the request's `proposedDate`, `proposedTime`, and sets `lastUpdatedBy = 'teacher'`.
   
2. **Counter-Proposal System (Ping-Pong Effect)**:
   - Once a date is proposed by one party, the other party's UI automatically shifts to display two buttons: **"Accept Proposed Date"** and **"Change requested Date/Time"**.
   - If the student clicks "Change", they submit a counter-proposal which switches the UI back so the teacher must now decide to accept or counter-propose again.
   - This back-and-forth relies on flipping the `lastUpdatedBy` variable continuously.

3. **Final Confirmation**:
   - The loop successfully terminates when either party clicks **"Accept Proposed Date"**.
   - The `handleNegotiationAction` automatically catches this click, switches the status to `demo_scheduled`, locks the finalized date, and ends the negotiation phase.

## Task: Real-Time Queue Verification & Auto-Cleanup
**Date:** August 8th, 2026

### What Was Done
Refactored the application queue logic to verify a teacher's pending request count directly against the database in real-time, preventing the "ghost application" bug caused by out-of-sync local arrays (e.g., when an admin manually deletes an application).

### Implementation Details
1. **Real-Time Verification**:
   - Updated `handleRequestTutor` and `handleDirectRequestDemo` in `student/page.tsx`.
   - Updated `handleSendOffer` and `handleDirectRequestDemo` in `teacher/page.tsx`.
   - Before executing a request, the logic now slices the local `pendingRequests` array and uses the `where(documentId(), 'in', reqIds)` operator to fetch the exact documents from the `applications` Firebase collection.
   - The system then actively counts only the requests that actually exist *and* have an active status, ensuring 100% queue count accuracy before enforcing the limit logic.

2. **Self-Healing Cleanup Mechanism**:
   - During the database fetch, the code compares the fetched results against the local array.
   - Any IDs in the local array that are missing from the database (or are no longer active) are categorized as "orphaned".
   - The system immediately triggers a background `updateDoc` on the teacher's profile, using `arrayRemove(...orphanedIds)` to seamlessly wipe the bad data.
   - This creates a self-healing environment where any desynced teacher profile will automatically correct itself the next time a request is attempted.
